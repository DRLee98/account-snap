# OCR-002 계좌번호/은행명 파싱 로직

## 문서 정보
- ID: OCR-002
- 생성일: 2026-05-28
- 참조문서: [OCR-001 CLOVA OCR API 연동](OCR-001-clova-integration.md), [DAT-001 Account 데이터 모델](DAT-001-account-model.md)
- 관계: 의존

## 목적

CLOVA OCR이 반환한 텍스트 배열에서 (1) 계좌번호 (2) 은행명 (3) 가능하면 예금주명을 식별·정규화.

## 입력

[[OCR-001]]의 `OcrResult` — 각 텍스트 박스의 `inferText`, `boundingPoly`(좌표), `inferConfidence`.

## 출력

```ts
type ParsedAccount = {
  accountNumber: string;   // 정규화 (하이픈/공백 제거, 숫자만)
  bankName: string;        // 표준 은행명 (예: "국민은행")
  bankCode?: string;       // 은행 코드 (있으면)
  holderName?: string;
  confidence: number;      // 0~1 종합 신뢰도
  candidates?: ParsedAccount[]; // 여러 후보가 나온 경우 (사용자 선택)
};
```

## 파싱 단계

### 1. 계좌번호 후보 추출

- 정규식: `/\d[\d\-\s]{9,}\d/` (숫자 10자리 이상, 하이픈/공백 허용)
- 후보별로 하이픈/공백 제거 후 길이 검증 (10~16자리)
- 한 매치의 숫자가 16자리를 넘으면 번호 두 개가 붙은 것 → 공백으로 분리.
  단, 분리된 조각이 **모두** 그 자체로 10~16자리일 때만 분리한다
  (한 번호가 여러 필드로 쪼개진 `"010" "1234" "5678"` 케이스를 잘못 합치지 않기 위함)
- 전화번호 형태(10~11자리 + 010/011/016/017/018/019 시작)는 **버리지 않고 문맥으로 판별** — 아래 1-1 참조

### 1-1. 평생계좌 vs 전화번호 판별

계좌번호가 곧 휴대폰 번호인 평생계좌(신한·국민·하나·농협 등)가 있어서, 접두사만으로 제외하면
평생계좌를 통째로 놓친다. 숫자 앞뒤 24자 문맥에서 가장 가까운 힌트 단어로 판단한다.

- 계좌 힌트: `평생계좌`, `평생`, `계좌`, `입금`, `송금`, `이체`, `통장`, `예금주` + 모든 은행 별칭
- 전화 힌트: `전화`, `연락처`, `휴대폰`, `문의`, `상담`, `팩스`, `Tel`, `H.P`, `phone` 등
- 앞쪽(before) 힌트가 뒤쪽(after) 힌트보다 강하다 — 뒤 단어는 다음 항목의 라벨인 경우가 많음
  (`"연락처 010-… 입금 국민은행 …"` → 앞의 `연락처`가 이김). 뒤쪽 거리에 +24 페널티.
- 판정 결과
  - **전화** → 후보에서 제외
  - **평생계좌** → 일반 계좌와 동일하게 취급
  - **문맥 없음** → 제외하지 않고 신뢰도 ×0.5 후순위 후보로 유지 (사용자가 선택)
    - 단, 이미지 어딘가에 `평생계좌`가 있으면 평생계좌로 승격
- 후보 정렬: 일반 계좌 > 평생계좌 > 문맥 없음 (동순위는 등장 순서)
- 12자리 이상은 `010`으로 시작해도 전화번호 검사를 하지 않는다 (일반 계좌번호)
- 표시 포맷은 은행 그룹 패턴보다 전화번호 형태가 우선 (`010-1234-5678` / `011-123-4567`)

### 2. 은행명 식별

- 사전 정의 은행명 리스트 매칭 (정확/부분 일치)
- 한글 표준명 + 영문 약어 + 흔한 오타 패턴 (예: "국민" / "KB" / "kookmin")
- 매칭된 은행 → 표준명 + bankCode 매핑

```ts
const BANKS = [
  { code: '004', names: ['국민은행', 'KB', '국민'] },
  { code: '088', names: ['신한은행', '신한'] },
  { code: '020', names: ['우리은행', '우리'] },
  { code: '081', names: ['하나은행', '하나'] },
  // ... 카카오뱅크, 토스뱅크, IBK, NH, SC, 우체국 등
];
```

### 3. 예금주명 추출 (옵션)

- "예금주" 단어 근처 텍스트 박스 (boundingPoly 좌표 기준)
- 한글 2~4자 + 영문 1~30자

### 4. 신뢰도 계산

- 계좌번호 매칭 confidence (CLOVA inferConfidence 평균)
- 은행명 매칭 확실성 (정확 1.0, 부분 0.7, 추정 0.4)
- 종합 가중 평균

## 엣지 케이스

- 한 이미지에 계좌 여러 개 → `candidates`로 다 반환, UI에서 선택
- 은행명 못 찾으면 → `bankName: ''` + UI에서 사용자 선택 드롭다운
- 계좌번호만 있고 은행명 없음 → 일부 은행은 계좌 prefix로 추정 가능 (정확도 낮음, 보조용)

## 수정 이력

### 2026-08-04 — 평생계좌(전화번호 형식) 인식

기존에는 `010/011/016/017/018/019`로 시작하는 숫자를 전화번호로 간주해 후보에서 무조건
제외했다. 계좌번호가 휴대폰 번호인 평생계좌가 통째로 인식되지 않았고, `010`으로 시작하는
12자리 이상 일반 계좌번호까지 같이 버려졌다.

- 접두사 무조건 제외 → 앞뒤 문맥 힌트 기반 판별로 교체 (위 1-1)
- 전화번호 형태 판정을 10~11자리로 한정 (12자리 이상 오탐 제거)
- 번호 두 개가 붙어 한 매치로 잡히던 문제 분리 처리 — 이전에는 길이 초과로 둘 다 사라졌음
- 중복 번호 후보 dedup
- `formatAccountByBank`에 전화번호 형태 그룹화 추가

### 2026-10-16 — 기울어진 간판에서 계좌번호 자릿수 순서가 뒤섞이던 문제

농협 간판 `352 8311 0141 93`이 `352-8311-9301-41`로 저장된 사례. 숫자는 전부 맞는데
마지막 그룹 `93`이 `0141` 앞으로 와 있었다.

**원인** — 파서는 숫자 토큰을 재배열하지 않는다. CLOVA가 돌려준 필드 순서를
`fields.map(f => f.inferText).join(' ')`로 그대로 이어붙였는데, 간판이 오른쪽으로 갈수록
위로 올라가게 기울어져 있으면 CLOVA의 좌표 기반 정렬이 줄 끝 단어(`93`)를 앞으로 보낸다.
필드마다 오는 `boundingPoly`를 전혀 쓰지 않고 있었다.

**수정** — `src/services/ocr/readingOrder.ts`에서 좌표로 읽기 순서를 직접 정한다.

- 박스를 x 순으로 훑으며 **바로 왼쪽 이웃**과 세로 겹침(작은 쪽 높이의 50% 이상)이면
  같은 줄로 묶는다. 줄 평균이 아니라 이웃과 비교하므로 기울어진 줄도 따라간다.
- 줄 순서는 각 줄 첫 박스(왼쪽 끝)의 세로 중심 기준.
- `clovaParser.joinClovaFields`가 이 정렬을 거쳐 이어붙인다. 좌표가 없는 필드가 하나라도
  있으면 원래 순서 유지.
- 온디바이스 OCR(OCR-003)도 같은 문제가 있어 네이티브가 블록 좌표를 함께 넘기고
  `deviceClient`에서 동일하게 재정렬한다.
- 재현 테스트: `__tests__/readingOrder.test.ts` (실제 좌표 배치를 흉내 낸 케이스)

### 2026-11-19 — 같은 간판에서 숫자 순서가 다시 뒤섞인 문제 (352 8311 93 0141)

**증상** — 2026-10-16에 고친 "농협 / 정원욱 352 8311 0141 93" 간판을 다시 찍었더니
`352-8311-9301-41`(3528311930141)로 저장됐다. 결과 화면의 사진 상자는 네 덩어리를 모두 감싸
OCR 자체는 숫자를 제대로 읽었고, 순서만 틀렸다.

**원인** — 줄 묶기가 새 상자를 **그 줄의 마지막 상자 하나**와만 비교했다. 가운데 덩어리 "0141"이
앞뒤보다 높이의 절반 넘게 처져 있으면(휘어진 간판·원근·OCR 상자 오차) "0141"은 혼자 새 줄이 되고,
다음 "93"은 "0141"을 건너뛰어 "8311" 줄에 붙는다 → `352 8311 93` + `0141`.
좌표를 넓게 바꿔 가며 재현해 보니 틀리는 경우의 대부분이 이 형태였다 (구 알고리즘 23% → 수정 후 5%,
남은 5%는 숫자 상자가 위 줄과 더 많이 겹칠 만큼 극단적으로 어긋난 경우).

**수정** — `sortReadingOrder`
- 묶은 뒤 **같은 줄 조각을 합친다**: 가로로 겹치는 상자가 없고(위아래로 쌓인 줄이 아님) 두 줄의 세로 띠가
  줄 높이의 30% 이상 겹치면 한 줄로 본다. 합친 줄 안은 x 순서로 다시 정렬
- 좌표가 깨진 상자(NaN)는 맨 뒤로 — 비교 함수가 NaN을 돌려주면 정렬 전체가 흔들린다
- CLOVA 꼭짓점에서 0인 좌표가 빠져 와도(`{ "y": 12 }`) 0으로 본다 (`clovaParser` `toBox`)
- 재현 테스트: `__tests__/readingOrder.test.ts` "가운데 덩어리가 처져 있어도…", "위아래로 쌓인 줄은…", NaN·빠진 좌표

### 2026-11-19 (2) — CLOVA가 텍스트를 엉뚱한 상자에 붙여 보내는 문제 (352 8311 93 0141)

**증상** — 위 수정을 적용하고도 같은 간판이 `352-8311-9301-41`로 나왔다.
안드로이드 실기기 재현 결과, 같은 사진·같은 빌드인데 **칠한 범위에 따라 갈렸다**:
숫자 줄과 은행명 줄만 좁게 칠하면 정상(`352-8311-0141-93`), 간판 전체를 넓게 칠하면 오류.

**원인** — 앱이 아니라 CLOVA 응답이다. 같은 이미지를 앱과 같은 엔드포인트로 직접 호출해
원본 `boundingPoly`를 받아 보니, `inferText`가 서로 다른 상자에 붙어 왔다.

| inferText | x | 상자 너비 | 글자당 폭 |
|---|---|---|---|
| `352` | 527 | 393 | 131 |
| `8311` | 948 | 476 | 119 |
| `93` | 1450 | 497 | **248** (2글자인데 4글자 폭) |
| `0141` | 1991 | 289 | **72** (4글자인데 2글자 폭) |

반환된 좌표로 이미지를 잘라 보면 `93` 상자 안에는 실제로 `0141`이, `0141` 상자 안에는 `93`이 있다.
**상자 위치는 맞고 텍스트만 뒤바뀐 것**이라, `sortReadingOrder`가 x로 아무리 정확히 정렬해도
`93`(x1450) → `0141`(x1991) 순서가 되어 3528311930141이 나온다. 좌표 기반 정렬로는 고칠 수 없다.
원본 해상도·3배 확대·기울기 보정(-2.3°) 모두 동일하게 재현됐다.

**수정** — `readingOrder.repairSwappedTexts`
한 줄 안에서 글자당 폭이 거의 일정하다는 점을 이용해, 상자 너비로 글자 수를 역산하고
실제 글자 수와 크게 어긋나는 상자들끼리만 텍스트를 바꿔 끼운다.
- 기준 글자당 폭은 그 줄 숫자 상자들의 **중앙값** (어긋난 값이 양쪽 극단에 있어도 안정적)
- 숫자(`^[0-9]+$`) 상자만 대상 — 한글·기호는 글자당 폭이 제각각이라 기준이 안 됨
- 숫자 상자가 3개 미만이거나, 어긋난 상자가 성한 상자보다 많으면 중앙값을 못 믿으므로 손대지 않음
- 역산 글자 수가 **0.75자 이상** 어긋날 때만 의심하고, 바꿔 끼운 뒤 **0.5자 이내**로
  전부 들어오는 배치가 있을 때만 적용 (원근으로 한쪽이 조금 커지는 정상 케이스는 통과)
- 맞아떨어지는 배치가 없으면 원본 유지 — 틀린 추측보다 원본이 낫다
- CLOVA·온디바이스 양쪽 경로에 함께 적용된다 (`sortReadingOrder` 안에서 호출)

**검증** — 실측 CLOVA 좌표를 그대로 넣은 회귀 테스트 추가
(`__tests__/readingOrder.test.ts` "실측 CLOVA 응답에서 뒤바뀐 …"), 오탐 방지 케이스 5개 동봉.
안드로이드 실기기에서 실패하던 "전체 넓게 칠하기" 케이스가 `352-8311-0141-93`으로 정상 복구됨.

**남은 한계** — 글자 수가 같은 두 덩어리가 뒤바뀌면(예: `8311`↔`0141`) 폭이 같아 구분할 수 없다.
그 경우는 이 보정으로 잡히지 않는다.

### 2026-11-18 — 다른 단어에 붙은 숫자 합쳐짐 + 은행 형식 검증

`계좌이처 농협 소떡소떡 000 떡꼬치2 352-18015-94-13 반선과` → `2352180159413`으로 저장된 사례.
원인이 두 개였다.

1. **파서**: 번호 정규식이 공백을 구분자로 허용해, `떡꼬치2`의 `2`까지 번호 앞에 붙였다.
   매치의 앞/뒤 토큰이 한글·영문에 붙어 있으면 떼어낸다 (토큰이 하나뿐이면 유지).
2. **OCR 오인식**: 1.1.0 기기 내 OCR이 좁은 글씨체를 `18015-94-13`으로 잘못 읽었는데,
   엔진 신뢰도가 높게 나와(Vision accurate는 0.5/1.0처럼 뭉뚱그려 나옴) CLOVA 폴백이 안 됐다.
   → `matchesBankFormat`: 자릿수가 은행 `lengths`에 없거나, 하이픈 그룹이 은행 `groups`와
   다르면 `formatMismatch`. 기기 내 결과가 불일치면 신뢰도와 상관없이 CLOVA로 재확인.
   - 텍스트에서 은행명을 찾은 경우에만 검증 (앞자리 추측 은행은 근거가 약함)
   - 공백 구분은 OCR이 임의로 쪼갠 것일 수 있어 그룹 검사 없이 자릿수만
   - 평생계좌 형태는 검사하지 않음
   - 기준표 보정: 국민 `6-2-6`, 지역농협 14자리 `6-2-6` 추가, 우체국 lengths 13→14(그룹 합과 모순)
   - 실사용 백업 16건 재검증: 오인식 1건만 불일치로 걸림
